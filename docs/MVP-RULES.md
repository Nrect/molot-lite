# Molot-lite: правила шаблона

> Это контракт шаблона для быстрых проектов: MVP, фриланс, внутренние сервисы. Правил намеренно мало — десять. Их сила не в строгости, а в том, что каждое закрывает конкретный способ, которым MVP превращается в болото. Старший брат шаблона — [Molot](https://github.com/Nrect/molot): серьёзная архитектура для серьёзных систем. Lite спроектирован как его подмножество: проект, выросший из lite, взрослеет в сторону Molot по одной фиче за раз, без переписывания.

## Почему MVP захламляется (и что мы с этим делаем)

Болото начинается не с простого кода — простой код это нормально. Оно начинается, когда у кода нет места: хендлер лезет в чужую таблицу, утилита оседает в `utils/`, бизнес-правило дублируется в третьем сервисе, и через полгода удалить фичу страшнее, чем дописать новую. Лекарство — не слои на каждый чих (их дисциплину на дедлайне никто не выдержит), а **жёсткие границы при простом наполнении**. Граница здесь — папка фичи.

## Структура

```
molot-lite/
├── cmd/server/main.go        # один процесс: конфиг, платформа, фичи, HTTP
├── internal/
│   ├── platform/             # инфраструктура, ноль бизнеса (см. правило 7)
│   │   ├── config/           # env, fail-fast со списком ВСЕХ проблем разом
│   │   ├── logs/             # slog: JSON в проде, text локально
│   │   ├── errs/             # slug-ошибки + единый маппер в HTTP-статусы
│   │   ├── auth/             # JWT (bcrypt-логин в фиче users), middleware
│   │   ├── postgres/         # pgx-пул, RunInTx, goose-миграции
│   │   └── server/           # chi, middleware-стек, healthz/readyz
│   └── <фича>/               # ВСЁ про фичу в одной папке:
│       ├── handler.go        #   HTTP: распаковка, вызов, маппинг ошибок
│       ├── service.go        #   логика простыми функциями
│       ├── storage.go        #   SQL этой фичи (и только этой)
│       ├── migrations/       #   goose-миграции фичи
│       └── <фича>_test.go    #   httptest на ручки + юнит на логику
├── docs/MVP-RULES.md          # этот файл
└── docker-compose.yml         # postgres; вся локалка одной командой
```

## Десять правил

**1. Фича — это папка.** Всё про лоты живёт в `internal/lots/`: ручки, логика, SQL, миграции, тесты. Проверка границы: фичу можно удалить, удалив папку и её строчки в `main.go`. Если после удаления что-то сломалось в другой папке — граница протекла, чините сразу.

**2. Чужие таблицы не трогаем.** Фича пишет и читает только свои таблицы. Нужны данные соседа — зовите его сервис-функцию (обычный вызов, без интерфейсов и церемоний). Это единственное правило про связи между фичами, и оно же — будущая граница bounded context, если проект вырастет.

**3. Transaction script — это норма.** Логика в `service.go` — простые функции: проверил, посчитал, сохранил, вернул. Никаких агрегатов, доменных событий и CQRS, пока на то нет причин (см. триггеры ниже). Стыдиться простого кода не надо; надо стыдиться простого кода, размазанного по проекту.

**4. Хендлер тонкий.** Распаковал запрос, достал юзера из контекста, вызвал функцию сервиса, замапил ошибку. Бизнес-`if` в хендлере — это переезд в `service.go`, без обсуждений.

**5. Ошибки — слаги, статусы — в одном месте.** Сервис возвращает `errs.NotFound("lot-not-found")`, и только маппер платформы превращает это в 404. Никаких `http.Error` и магических чисел по хендлерам — иначе через месяц у вас четыре формата ошибок.

**6. Интерфейс — только когда есть второй.** Второй вариант хранилища, фейк для теста, внешний API, который надо подменять. Нет второго — зовите конкретный тип. Интерфейс «на всякий случай» — это и есть начало захламления.

**7. В `platform/` нет бизнеса.** Слова «лот», «ставка», «юзер» в платформе не встречаются. Появилось желание положить туда «общую бизнес-утилиту» — она едет в фичу, которой принадлежит, или дублируется (да, дублируется: см. Molot, правило про DRY к поведению, не к данным).

**8. Никаких `utils/`, `helpers/`, `common/`-свалок.** Хелпер нужен одной фиче — живёт в ней. Двум — это либо платформа (если инфраструктура), либо честный дубль (если бизнес). Папка-свалка запрещена по имени.

**9. Конфиг из env, падать на старте.** Все настройки через переменные окружения, отсутствие обязательной — ошибка при запуске со списком всех проблем разом. Захардкоженный секрет или URL — дефект.

**10. Тесты пишутся сразу, но дёшево.** На каждую ручку — httptest (запрос и ответ, реальная БД из compose), на хитрую логику — табличный юнит. Без моков, без слоёв тестов, без погони за покрытием. Тест — это способ не открывать Postman после каждой правки.

## Триггеры взросления

Шаблон не запрещает сложность — он откладывает её до доказанной нужды. Вот сигналы, после которых фича дозрела (рецепт перехода — глава 19 книги Molot):

| Сигнал | Что делать |
|---|---|
| В `service.go` стена if-ов вокруг одного понятия, правила дублируются | Выносите доменный тип с методами внутрь папки фичи (рождается `domain.go`, затем `domain/`) |
| Второй потребитель данных фичи, «сделай после того как» между фичами | Событие и подписка вместо прямого вызова (в Molot это шина с outbox) |
| Процесс длиннее одного запроса: оплата с ожиданием, многошаговая выдача | Машина состояний, затем сага (Molot, глава 10) |
| Фича стала продуктом: своя команда, свой релизный цикл | Полные слои внутри папки, затем вынос — граница уже стоит (правила 1–2 её держали) |
| Появились деньги | Не ждите триггеров: идемпотентность операций и аудит движений с первого дня (Molot, глава 11) |

## Чего здесь нет и почему

Нет CQRS, событий, outbox, саг, OpenTelemetry, OpenAPI-кодогенерации, in-memory реализаций, декораторов. Не потому что это плохо — в Molot всё это есть и оправдано. Здесь это убрано, потому что для проекта на месяц-три каждый из пунктов — налог без выгоды, а недособлюдённый паттерн хуже отсутствующего. Что остаётся всегда: границы (правила 1–2), один формат ошибок, конфиг, миграции, тесты. Этого хватает, чтобы код через полгода всё ещё можно было читать — и чтобы дорога к взрослой архитектуре оставалась открытой.
